# 学祭精算 v2.0 — 全員共有版

GitHub Pages（画面）＋ Supabase Free（認証・DB・リアルタイム変更通知）を利用するスマホ対応Webアプリです。コードは静的な HTML/CSS/JavaScript。売上明細は管理せず、売上総額・費用・留保金から、貢献ポイントに応じて利益を1円単位で分配します。

## 1. GitHub Pagesの準備（現在のv1をv2に更新）

- **現在のGitHubリポジトリをそのまま使用**します：`https://github.com/hashiyo7u1ta4-cmd/gakusai-settlement`
- ZIPの中身を展開し、**フォルダそのものではなく、中身をリポジトリ直下**に配置してください。`index.html`, `app.mjs`, `engine.mjs`, `cloud-model.mjs`, `styles.css`, `cloud.css`, `config.js`, `sw.js`, 画像類、`manifest.webmanifest`, `.nojekyll` が必要です。
- `supabase/setup.sql`, `README.md`, `tests/` は公開しても構いませんが、GitHubに個人の記録を含んだJSONやパスワードを置かないでください。古いv1用のファイルは上書きしてください。
- リポジトリの `main` ブランチの `/(root)` から GitHub Pages公開のままで動きます。URLも変わりません。
- **まだ Supabase を設定していないときは接続設定案内だけが表示されます。** 先にSupabaseの設定を行ってください。

## 2. Supabaseで無料プロジェクトを作成

1. `https://supabase.com/dashboard` でログインし、**Free** の新規プロジェクトを作成。課金プランへのアップグレードは不要です。DBパスワードは自身で保管してください。
2. Supabase の **SQL Editor → New query** に、同梱の **`supabase/setup.sql` の全文**を貼り付け、**Run** で一度だけ実行します。既存テーブルのあるプロジェクトでは実行しないでください。新規専用です。
3. **Authentication → Providers / Sign In → Anonymous Sign-Ins** （UI表記は変わる場合があります）で、**Allow anonymous sign-ins** を ON にします。これが OFF だと参加時にログインできません。
4. 必要に応じて **Authentication → Bot and Abuse Protection** で CAPTCHA を設定し、匿名サインインの乱用を防いでください。今回は CAPTCHA のフロントエンド連携は未実装です。小規模な限定運用から開始してください。
5. **Project Settings → API Keys** （画面によっては **Connect**）で次を確認します。
   - **Project URL**：`https://xxxxxxxx.supabase.co` の形式
   - **Publishable key (`sb_publishable_...`)** または legacy **anon key** (`eyJ...`)。**secret key / service_role は使用禁止**です。

### `config.js` を編集

GitHubリポジトリのルートで `config.js` を開き、鉛筆マークから以下の2箇所を書き換え、**Commit changes** します。

```js
window.GAKUSAI_CONFIG = {
  url: 'https://xxxxxxxx.supabase.co',
  key: 'sb_publishable_xxxxxxxxxxxxxxxxxxxxxxx'
};
```

Publishable/anon キーはブラウザに公開するためのキーです。アクセス制限はDBのRLSで実施します。**service_role・secret key・DBパスワードは公開厳禁。**

Supabaseプロジェクトが Free プランのため、アクセスがない状態が続くと自動停止することがあります。学祭前にはアクセスして動作確認してください。

## 3. 最初の管理者の操作

1. `https://hashiyo7u1ta4-cmd.github.io/gakusai-settlement/` を開き、「**新規作成**」を選択。
2. 出店名と自分の表示名を入力。「**作成する**」で匿名ログインとイベント作成が行われます。
3. 表示された2つの異なる32桁のキーを区別して保管：
   - **招待コード**：参加者全員に共有してよい。これだけでは管理者になれません。
   - **管理者復旧キー**：管理者だけが安全な場所に保管。他人に渡さない。別端末・ブラウザの管理者権限復旧にも利用可能。
4. 「参加者・設定」でポイント配点・売上・留保金を設定。招待コードを参加者へ共有します。

招待コードと管理者復旧キーの**平文はSupabaseに保存しません**。暗号学的ハッシュのみ保存し、キーの実物は作成したブラウザ内に一時保管されます。安全な別の場所に控えてください。コードの再生成後は以前のコードが無効になります。

## 4. 参加者の操作

1. 全員同じ GitHub Pages URLを開く。
2. **参加** → 名前＋**招待コード**で参加。メールアドレス・パスワードは不要。
3. 「貢献記録」から自分の作業回数を登録。「立替・経費」から自分が払った費用を登録。「資金・精算」から運営金庫に渡した資金を記録。
4. これらは一般参加者からの**承認待ち**として保存され、管理者が「承認待ち」で確認して承認すると計算に反映。
5. 全員が精算結果と記録履歴を見ることができます。

管理者は他の人の申請の代わりに記録を追加できます。その場合は承認済みとして登録されます。**売上・配点・送金確定・承認は管理者だけ**が変更できます。SupabaseのRLS＋列権限で保護します。

### 匿名IDの重要な制約

- 匿名IDは**ブラウザに保存されたセッションに紐付きます**。端末変更、ブラウザデータの削除、サインアウト後には同じユーザーIDへ戻れません。
- 新しい端末では新しい参加者アカウントになり、過去の記録は元の表示名のまま残ります。管理者が同じ名前に見えても別の参加者として扱われます。
- 管理者は「**管理者復旧**」から、別端末で管理者復旧キーを入力することで新しい管理者IDを追加できます。ただし以前のIDと**精算上は別の参加者**です。
- **端末をまたいでも同一個人として扱う本人確認や、ユーザー統合機能は未実装**です。ポイント精算の前に重複登録がないか確認してください。

## 5. 会計上のルール

- **分配対象利益 = 売上 − 承認済み全経費 − 留保金**
- **個人配分額 = 分配対象利益 × 個人の承認済み貢献ポイント ÷ 全員の承認済みポイント**（端数は最大剰余方式で1円単位に調整）
- **個人の残額 = 配分額 + 承認済み個人立替 + 承認済み資金拠出 + 支払済み - 受取済み**
- 運営金庫から支払った経費は立替返金になりません。参加者自身が支払った経費だけが立替返金対象。
- 赤字時と、利益があるのにポイントが未登録のときは精算案を自動停止。
- 設定の配点を変更しても過去の記録のポイントは変わりません。
- **送金記録は実際の支払が完了してから管理者が登録**。アプリ自体に振込機能はありません。
- 承認済み申請をキャンセルしたいときは管理者が承認を取り消せます。送金履歴は削除不可のため、誤記入があったら反対向きの送金記録で相殺する運用です。

## 6. データの保存・バックアップ

- データ本体はSupabaseに保存します。ブラウザ内には認証セッションと、参加中のイベントID・管理者が作成したコードのみ保存します。
- Supabase Realtimeで変更通知を受信し、さらに25秒ごとに更新確認します。通信が切れた場合は同期できません。
- 「参加者・設定」でJSONバックアップとCSV出力ができます。**このv2では JSONの復元・v1の自動移行は未実装**です。
- v1のブラウザ保存データは破棄しませんが、v2では自動的に読み込みません。**v1で既に記録がある場合は、更新前にv1でJSONバックアップを取り、v2への移行について相談してください。**
- 金銭記録を扱うため、管理者は精算前に各種申請と金庫残高を実際の帳簿・現金と照合してください。

## 7. 無料運用について

- GitHub Pages : 公開リポジトリの静的サイト。通常無料。
- Supabase Free : 共有DB、認証、Realtime。**無料枠の容量・トラフィック・プロジェクト数・自動停止等の制限があります**。クレジットカードの支払いを伴うアップグレードは不要です。
- Supabase標準のメール送信はプロジェクトチーム宛制限や毎時送信数制限があるため、メールOTPは使わず匿名認証を選択しています。
- 利用者本人のID復旧を重視する場合は、次の段階でGoogle OAuth等の恒久認証を検討してください。

## 8. テスト

```bash
node --test tests/*.test.mjs
```

精算計算と「未承認の記録を精算に含めない」ロジックの自動テストを用意。現時点では開発環境から実際のSupabaseプロジェクトに接続した権限・同期の統合テストは**未実施**です。本番で金銭の精算に使う前に、管理者と一般参加者の**異なる2端末**で下記を確認してください。

1. 管理者Aが出店を作成し、参加者Bが招待コードで参加できる。
2. Bが自分の立替・貢献を追加すると、Aにも承認待ちと表示される。
3. 承認前は金額に反映されず、Aが承認すると両端末の計算結果が更新される。
4. Bが他人の記録・配点・売上・送金を変更できない。
5. 金庫から実際に支払った後にAが送金履歴を登録し、残額が減る。
