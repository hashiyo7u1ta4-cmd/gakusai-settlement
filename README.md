# 学祭精算 v4.0 — 出店一元管理（ローカル検証版）

v3の「Googleログイン／参加者ID／貢献ポイント／立替・拠出／承認／利益配分」を維持し、POS・商品・原材料・仕入れ・現金点検・レジ締め・売上照合・利益分配確定を追加した **1本のv4.0** です。PC・スマートフォンのブラウザで利用できます。

**このZIPはローカル検証用です。本番GitHub Pagesと本番Supabaseには適用しないでください。**

## v4機能

| ページ | できること |
|---|---|
| レジ・POS | レジを登録、会計セッションを開始、商品タップで買い物かご、現金・キャッシュレス会計、釣銭計算、全額返金、売上履歴 |
| 商品管理 | 商品名・価格・分類・販売状態・完成品在庫・消費材料レシピ |
| 在庫・仕入れ | 材料・単位・最低残量・棚卸・廃棄・数量調整、仕入れ・入庫・経費の同時登録、立替人の選択、必要に応じレジ現金出金の同時記録 |
| 現金点検 | レジごとの釣銭準備金、営業時間中の随時現金点検、レジだけ一時停止、差額と原因、再開、入出金履歴、日次レジ締め、キャッシュレス照合 |
| 売上照合 | POS純売上と従来手入力分を別表示、帳簿売上／実査差額を照合、差額理由入力、全レジ締めと申請承認後の管理者最終確定、CSV |
| 既存ページ | 参加者の事前登録・Googleログイン・表示名変更・ポイント・立替・拠出・精算履歴・JSONバックアップ |

### 売上と現金の計算原則

- **帳簿売上** = 従来入力のPOS以前の売上 + POS販売額 − POS返金額（レジで受け取った額・お釣りとは別）。
- **レジ理論現金** = 開始時釣銭準備金 + 現金販売 − 現金返金 + レジ現金入金 − レジ現金出金。
- **現金差額** = 閉店時の実査現金 − 理論現金。中間点検は履歴を残すが売上を修正しない。
- **キャッシュレス差額** = 決済端末等で確認した純額 − POSキャッシュレス純額。
- **分配対象利益** = 帳簿売上 − 承認済み経費 − 留保金 − 過不足による不足分。現金・キャッシュレス過不足の合算がプラスでも超過分は自動配分しない。
- **立替返済、資金拠出返金、貢献ポイント配分**は既存v3の独立した計算を維持する。仕入れ連動登録時は同一操作から経費を1件作成する。別途同じ領収書を登録しない。
- 商品・材料の販売減算と注文確定はサーバー側の**単一DBトランザクション**。同じレジの販売・点検をレジセッションの行ロックで直列化する。会計トークンの重複は二重売上を防ぐ。
- 最終確定後は帳簿・貢献・費用・会員構成等の変更をサーバーで拒否。**本人の表示名変更と、既に確定した送金の支払い済み記録**は継続可能。

### 権限

- Googleログインしたイベント参加者：商品・在庫・売上等の閲覧、通常POS販売、任意の現金点検、本人の貢献・立替の申請、表示名変更。
- 管理者：商品・材料・在庫・仕入れ・レジ開閉、現金入出金、返金、申請承認、最終利益分配確定、送金済みの記録。
- 変更APIはDBのRPCで実行し、POS等のテーブルの直接INSERT/UPDATE/DELETE権限を一般ログインユーザーに渡しません。RLSはイベント所属者だけにデータを表示します。

## 1. v3開発DBをバックアップ

**v3がローカル動作している開発専用Supabaseプロジェクト**を使います。イベント・メンバー・経費等を先にバックアップしてください。既存のv3の`setup.sql`や`upgrade_v2_to_v3.sql`を再実行しないでください。

## 2. Supabase SQL Editorで v4追加SQLを一度だけ実行

`supabase/upgrade_v3_to_v4.sql` を全選択して貼り付け、**開発用DBだけ**で実行します。

- v3のテーブルは削除しません。商品・材料・レジ・販売・点検・在庫・仕入れ・最終確定のテーブルと操作関数を追加します。
- SQLは追加マイグレーション用で**繰り返し実行できるようにはしていません**。「既に存在します」と出る場合は再実行を止め、SQLの実行状態を確認します。
- 新規の空DBなら、まずv3 `supabase/setup.sql`を実行し、**次にv4の追加SQL**を実行してください。
- 本番プロジェクトに移行する場合は必ず先にステージングへバックアップ・復元して移行テストを行ってください。本番移行は別途承認後です。

## 3. config.jsを設定（開発専用Supabase）

`config.js` にすでにローカルv3で利用した開発専用 `Project URL` と `Publishable key` を設定します。再配布ZIPは意図的にプレースホルダーです。

```js
window.GAKUSAI_CONFIG = {
  url: 'https://DEVELOPMENT_PROJECT.supabase.co',
  key: 'sb_publishable_DEVELOPMENT_KEY'
};
```

ブラウザから実行するための公開キー以外は設定しません。**service_role、secret、DBパスワード、Google OAuth Client Secretは設定禁止です。**

## 4. ローカル起動

PowerShellで展開したv4フォルダへ移動後：

```powershell
python -m http.server 8000 --bind 127.0.0.1
```

アクセス：`http://localhost:8000/`

v3と同じGoogle Cloud OAuth / Supabase Authentication設定で動かします。Googleログイン後、同じ出店を選びます。以前の開発DBの会員ID・立替・貢献は引き継がれます。

以前のv3のService Workerが残っている場合、`Ctrl + Shift + R` で強制再読み込みしてください。必要に応じブラウザの開発者ツール → Application → Service Workersから旧版の登録解除を行います。データベース内の会計記録は消えません。

## 5. 一連の検証手順（推奨）

1. 管理者でGoogleログイン。v3の参加者・精算を確認。
2. 商品に「焼きそば 500円」、材料に「麺（玉）」を登録。材料を仕入れ、立替人と購入金額を指定。材料在庫・経費が同時に増えることを確認。
3. レシピを「焼きそば1食 → 麺1玉」に設定。完成品在庫を管理する場合は商品在庫を入庫。
4. レジを登録、開始時釣銭準備金10,000円で開局。
5. 焼きそば2食（1,000円）を現金2,000円預かりで販売。釣銭1,000円、レジ理論現金11,000円、麺在庫−2を確認。
6. 「中間現金点検」を開始し、ほかの端末で**同じレジの会計が停止**されることを確認。現金10,900円なら−100円で差額理由の入力が必須。点検完了後に営業継続を確認。
7. キャッシュレス会計、レジ現金入出金、全額返金（必要に応じ在庫復帰）も確認。
8. レジを締め、現金実査と決済端末の確認額を入力。差額があれば備考必須。複数レジ・複数日を試す。
9. 参加者の申請を承認して最終分配を確定。確定前は送金案を停止し、確定後の金額・会員・経費変更はDB側で拒否されることを確認。実際に払った送金の記録は継続可能。
10. 金銭データは複数端末を同時操作して一致すること、CSVとJSONでデータの書き出しを確認。

## 7. 現在の対象外・制限

- **部分返金・混合決済（現金＋キャッシュレスの併用）**：初版は全額返金・支払い手段1種類に限定。
- **現物の決済処理**：キャッシュレス端末や銀行とは連携せず、決済完了額を手入力して照合。振込そのものは行いません。
- **損益の税務・会計基準への完全準拠**：学祭内部管理用です。税込価格を前提とし消費税申告・会計監査向け帳簿ではありません。
- **JSONの直接復元**：バックアップ閲覧・外部保管のみ（復元機能未実装）。個人情報が含まれるためGitHubの公開領域にアップロードしないでください。
- **サービス利用の無料枠**：GitHub Pages / Supabase Free を使用します。Supabaseの容量・無料枠制限および将来の料金体系はサービス側に依存します。
